# What's missing for an unattended loop: findings from DEVEX-528 (v1)

Each row is something we had to add, work around, or do by hand to get one ticket through the trainer's loop. It's ordered
along the diagram. **Observed** = it happened during this exercise; **Known** = found while reading the repo.

## Input (ticket)

| # | Gap | Evidence | Proposed fix |
|---|---|---|---|
| I1 | The Jira ticket is a two-sentence bug report: no acceptance criteria, no scope, no check, no platforms, no non-goals | Observed: DEVEX-528 vs `tickets/DEVEX-528.md`; a human (with an agent) wrote the spec | "Agent-ready" definition of ready + a triage agent that drafts the spec into Jira and asks the reporter; the existing `write-jira-ticket` skill is a start |
| I2 | No place in Jira for an executable acceptance command or the Touches/Do-not-edit scope | Observed | Jira fields or a templated description section; the ticket file in the repo is the stopgap |
| I3 | Writing the oracle is the hard part, and the first draft was wrong: it asserted on `source.Items` (a lazy view of the live list) and **passed on the buggy code** | Observed: 8/8 green on master until it asserted on `source.Rows` | Make "red on base, for the right reason" a mandatory gate before a ticket is agent-ready; record the red run in the ticket |

## Observed during the loop run (2026-10-21, base `fa1aad5e094`)

| Station | Result |
|---|---|
| Builder (Opus 5.5) | 3.0 min, 41 turns, $1.66, 0 permission denials. One code commit (`DevoDataGrid.axaml.cs`, +31/−2) plus record and hand-back, in the right order |

What the run taught us:

| # | Gap | Evidence | Proposed fix |
|---|---|---|---|
| R1 | **The loop is only as good as the oracle.** With the spec and a red test, the builder needed no help; all the hard work (and the one real mistake) was in writing the oracle (I3) | Builder succeeded on the first try; the first oracle was wrong | Invest in spec + oracle authoring (a "spec agent" step, human-approved) before investing in builders |
| R2 | The reviewer's claims can't be audited: `--output-format json` keeps only the final answer, so "re-ran: exit 0, 8/0" is unverifiable | `review-1.json` has 6 turns and no transcript | Use `--output-format stream-json` and keep the transcript as evidence; have the runner, not the reviewer, own the re-run |
| R3 | A 17-second, 6-turn review said merge with no findings, and missed what a human would ask: a full rebuild per burst re-applies selection and posts `ScrollToSelectedItem` (`DevoDataGrid.axaml.cs`, `EnsureSelection`), which may yank the Port Scan view while the user is scrolled away. **Unconfirmed**, but no sensor or lens looks at it | Reviewer output; code reading | Reviewer lens for UX side-effects of rebuilds; a runtime sensor (S3); a minimum-effort floor for the reviewer (must read callers, must list what it checked) |
| R4 | The cheapest station (verify) was the most trustworthy one. Deterministic checks found nothing wrong because the builder followed the rules, but they are what makes "ready for the judge" mean something | `verify-1.log` | Keep growing `verify()`: warnings delta, wider test set, performance budget (S4) |
| R5 | The judge still has to open the app: nothing in the hand-back shows the fix working in Port Scan | Hand-back "How we'd see it in production: test" | S3; the hand-back should carry a screenshot or recording for UI tickets |
