# What's missing in the VM toolkit

The VM layer was the factory skill's until it became this plugin (factory 0.8.0, vm-toolkit 0.1.0). These rows came with
it from the factory's `GAPS.md`, under the same numbers, so older notes and commits still find them; the factory's rows
about how its loop uses the VMs stayed there. **Observed** = it happened in a run; **Known** = found while reading.
Paths and names in the older rows are the factory's of the time (`/tmp/factory-smb-*` is `/tmp/vmt-smb-*` now, and a VM's
title comes from its caller, `VM_TITLE`).

| # | Gap | Evidence | Proposed fix |
|---|---|---|---|
| V4 | ~7+ min guest build per QA run, over SMB; a cold NuGet cache adds ~10 min | Known (rdm-windows-vm-test notes) | Warm the golden image (vm-setup.md step 3); later a booted snapshot (`savevm`) or building on a Windows CI runner |
| V5 | Blindness is by construction (cwd outside the repo, no Read rule, no git), but `vmssh` can still read the source through the guest's `R:` | Known | Share a build output only (publish folder) instead of the worktree |
| V6 | One guest platform (Windows). The DEVEX-528 bug is in the shared grid, so it shows there, but Mac-only and Linux-only bugs can't be checked | Known | macOS guest via Apple Virtualization (tart, clone per run, VNC; licence: 2 macOS VMs at once), Linux guest via QEMU, behind `vmctl.sh` |
| V7 | Each run starts from RDM's first-run state unless the golden image was warmed; dialogs eat QA turns | Known | Warm-up step in vm-setup.md; a seeded settings/data-source file per scenario later |
| V9 | `install.sh` only finds `Win11_*rm64*.iso`; Microsoft's current download is named `Windows11_Client_arm64_en-us_*.iso` | Observed (DEVEX-509 setup): "No Windows ISO" until `WIN_ISO=` was passed | Widen the glob to `*rm64*.iso` / `*arm64*.iso` |
| V10 | The "Press any key to boot from CD" prompt is ~5 s; missing it drops to the UEFI shell, where Enter does nothing | Observed: user landed in `Shell>`; recovered with `FS0:` then `EFI\BOOT\BOOTAA64.EFI` | Say so in vm-setup.md; or send the key over QMP right after boot |
| V11 | The guest gets a copy of the user's `NuGet.Config`, including Mac-only local sources (`/Users/<me>/Documents/NuGet`): every restore fails NU1301 | Observed: 852 errors in the first warm-up build; the guest copy also keeps the seed ISO's ReadOnly attribute, so `dotnet nuget remove source` and `Set-Content` fail silently over `vmssh` | Strip non-http sources when seeding (`install.sh`), or let `setup-guest.ps1` drop sources whose path doesn't exist and clear ReadOnly on the copy |
| V12 | A VM started with a plain `&` from an agent's foreground shell gets `nice 5` + macOS background throttling (QEMU and smbd): SSH and QMP calls hang for minutes, a screendump crawls at KB/s | Observed: warm-up VM via `start.sh … &`; `ps` NI=5, `sample` showed qemu_main in `write()` holding the BQL | Start VMs from a harness-tracked background task (or `vmctl.sh up`, which the runner owns); a preflight in `vmctl.sh` that warns when its own nice > 0 |
| V15 | **Fixed (2026-10-22).** Clones ran at 800×600 (ramfb; its firmware caps at 1024×768, and `factory-qa.md` claimed 1024×768): RDM's window and dialogs overflowed the screen, a human couldn't use it and the QA agent spent ~5–10 actions per run snapping windows | Observed: both DEVEX-509 QA reports start with Win+Up / snap steps; the judge asked for a usable screen | Clones and `start.sh` now use `virtio-gpu-pci` at `VM_XRES`×`VM_YRES` (1600×900); the golden image carries `viogpudo` (WHCP-signed ARM64), and `autounattend.xml` installs it for new images |
| V18 | **Fixed (2026-10-22).** The share could be missing when the guest build started (QEMU starts the host's smbd on the first connection; slower with two VMs booting), `vmssh` mapped `R:` once and ignored the error, and the build ran outside the worktree: a harness failure reported as **FAIL: the build fails**, which a full loop would have sent back to the builder | Observed: first DEVEX-509 regression runs after the decoupling, both `MSB1009` in 0 s, smbd log 8 s after the build started | `vmssh` retries the mapping for 60 s; the target's build stops without `BUILD EXIT CODE` when `R:` is missing, so the runner says ERROR |
| V19 | **Fixed (2026-10-22).** `vmctl up` runs `gc`, which treated a slot claimed by a VM still starting (no QEMU yet) as dead and deleted its disk and firmware vars: two runs started together, one died with "Could not open vars.fd" | Observed: second DEVEX-509 regression pair | `up` marks its slot `starting` until QEMU runs; `gc` skips such slots unless the marker is older than 5 min |
| V21 | **Fixed (2026-10-22).** The guest's share stalled mid-build: Samba's runtime dirs hold Unix sockets, macOS caps a socket path at 104 characters, and moving the VMs to `~/VMs/factory/windows/runs/<run>/…` pushed it over. Every smbd after the first exited with `messaging_dgm_ref failed: File name too long` (459 restarts in 5 min), so every `R:` access hung. Intermittent: it depends on the run id's length and the smbd pid's digits | Observed: every DEVEX-509 regression after the move; found by raising the live run's smb.conf to `log level = 3` | Samba's private (its msg.sock lives there), lock, state, cache, ncalrpc and pid dirs go to `/tmp/factory-smb-<uid>-<slot>`; keep socket paths short whatever the VM root |
| V22 | Windows Update downloaded ~8 GB into the golden image's Delivery Optimization cache within a day of the install (plus a 1.5 GB kernel dump and a 5 GB system-managed page file): the image was 42 GB, more than a full RDM build needs | Observed: maintenance boot on 2026-10-23, `C:\Windows\ServiceProfiles\NetworkService\…\DeliveryOptimization\Cache` | `golden/compact.sh` (42 GB to 18.3 GB, no slowdown). Not measured: whether each clone downloads updates into its overlay during a run. If it does, pause Windows Update in the image |
| V24 | A VM in a QEMU window (`start.sh` without `--headless`) stalled for ~35 min while the Mac's display was off: QEMU at ~0% CPU, QMP and SSH unanswered; it resumed by itself when the display came back on. Throttling of a windowed app with the display off is the likely cause (not verified); the Mac didn't sleep (`caffeinate`), and Spotlight re-indexing after a restart kept the load average at ~77 | Observed: devolutions-console layer maintenance boot, 2026-10-26 09:26-10:04; `pmset -g log` display off at 09:26, install started 09:27 | Run unattended maintenance headless (`build.sh` does); for a windowed boot keep the display awake (`caffeinate -d -w <qemu pid>`); exclude `~/VMs` from Spotlight |
| V25 | The Kestrel service's watchdog (`Worker.cs`) checks the server once, 10 s after start, and stops the service when it doesn't answer: a first start under x64 emulation (migrations behind a 503) is always slower, so a fresh Kestrel instance never comes up as a service | Observed: devolutions-console layer, 2026-10-26 | `setup.ps1` starts `Devolutions.Server.exe` directly until it answers 200, then the service. Product fix: retry or a longer grace period (DVLS team) |
| V26 | The `/dvls` Scheduler crashed at clone boot: SQL Server Express installs as Automatic (Delayed Start), so it wasn't up yet; delaying the Schedulers too only moved the race (SQL Express still stopped 3.5 min after boot) | Observed: clones of the devolutions-console layer, 2026-10-26 | `setup.ps1` sets SQL Express to Automatic and makes the `/dvls` Scheduler depend on it; applied to the frozen layer the same day, verified by a clone reboot (all Schedulers up, three sites 200) |
| V38 | **Fixed (2026-10-27).** The guest clock ran 4 hours ahead (QEMU gave a UTC hardware clock; Windows reads it as local time, Eastern). Files the guest wrote on the share looked newer than those edited on the host, so an incremental build skipped repacking a changed `.axaml`: verify stayed green and QA passed a build with the previous XAML. | Observed: DEVEX-517 run 3, qa-3 PASS on stale XAML (the DLL had the new C# property, the packed XAML did not). Fix: `-rtc base=localtime` on every QEMU command line; checked: guest UTC = host UTC, share mtimes match. Also closes V34. |
| V77 | **Fixed (2026-11-04, 0.7.5).** A VM shown in Screen Sharing was titled after its slot only ("QEMU (factory-2)"), so with several runs' VMs up nothing told which window was which run's build or QA VM. | Raised by the user, 2026-11-04. | QEMU's `-name` (the VNC desktop name, Screen Sharing's window title) is the ticket, what the VM is for and the run id, from its folder: "DEVEX-514 QA round 5 - devex-514-20261104T182338Z"; build, base re-check and tests-on-the-base VMs likewise. Not `process=` to keep the old name: QEMU on macOS refuses to start with it. |
| V87 | **Fixed (2026-11-11, 0.1.2).** A VM shown in Screen Sharing had no shared clipboard: nothing copied on the Mac (a long key) could be pasted in the guest, or back. | Raised by the user, 2026-11-11. Screen Sharing can't fix it: QEMU sends the guest's clipboard only to VNC clients with the extended clipboard (`ui/vnc-clipboard.c`), which it lacks. | Clones carry QEMU's vdagent port; `show` puts the SPICE agent in the VM on its first show (`clipboard.sh`, ~5 s: x64 agent under emulation, ARM64 virtio-serial driver) and opens TigerVNC, which shares the clipboard both ways (checked: 4 KB of Unicode, same SHA-256). Not in the golden image: the layers on it would no longer match. |
| V88 | **Fixed (2026-11-11, 0.2.0).** Every VM started from the golden image or a layer, and its disk went at power-off (idle, `down`, the next `up`): a sign-in a person did in the guest (third-party SSO, which a test credential can't replace), or setup the dev found it needed, was lost for the next VM, and for the same VM after 10 idle minutes. | Raised by the user, 2026-11-11, for FleetView's office (dev, then blind QA and exploratory QA on their own VMs). Checked by hand first: an RDM sign-in survived a clean shutdown, its disk frozen and a new VM started from it. | Checkpoints: `vmt checkpoint <vm dir> <name>` shuts the guest down cleanly, TRIMs, and freezes its disk as `<os>/checkpoints/<name>.qcow2` (read-only, ~1 GB, ~1 min); the VM and any other (`init --checkpoint`, `vm_up from_checkpoint`) start from it, each on its own throwaway copy. `list`, `show`, `rm` (refused while in use); only a person deletes one (no MCP tool). Not the worktree: settings an app keeps on `R:` stay on the Mac. |
| V89 | **Fixed (2026-11-12, 0.3.0).** Agents could take screenshots but not a video: a QA agent had no way to make a demo of a change for a person. | Raised by the user, 2026-11-11. First try: a recorder on the VM's QMP socket froze the guest's input until it stopped (QEMU serves a QMP socket to one client at a time). | Clones carry a second QMP socket for `vm/record.py`: PPM screendumps (8 ms) at 15 fps into the hardware encoder, then x264 (1 to 2 MB a minute). `app record start|stop`, `app caption` (`vm_record_start`, `vm_caption`, `vm_record_stop`); clicks circled. Captions drawn by AppKit (`overlay.js`): Homebrew's ffmpeg has no text filter. Checked on a VM: captions and rings on the right frames, a recording that hits its limit or a `down` keeps its video. |
